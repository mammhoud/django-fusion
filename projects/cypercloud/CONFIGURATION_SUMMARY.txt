================================================================================
CONFIGURATION HIERARCHY
================================================================================

Settings are loaded with this precedence (highest to lowest):
  1. Environment variables (TINKER_SECRET_KEY, TINKER_DEBUG, etc)
  2. Environment-specific YAML (configs/settings.{ENV}.yml)
  3. Base YAML (configs/settings.yml)
  4. Python defaults (settings.py)

This means:
  - Secrets can be set via .env or system environment
  - Each environment (dev/prod) can override settings
  - Base defaults apply to all environments
  - Python has safe fallback values

================================================================================
ENVIRONMENT DETECTION
================================================================================

Tinker automatically detects environment from (in order):
  1. TINKER_ENV environment variable
  2. DJANGO_ENV environment variable
  3. ENV environment variable
  4. ENVIRONMENT environment variable
  5. Defaults to "development"

Set it:
  export TINKER_ENV=production

================================================================================
TROUBLESHOOTING
================================================================================

Q: How do I set a secret key for production?
A: Generate one and set it in .env.production:
   python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
   echo "TINKER_SECRET_KEY=<generated-key>" >> .env.production

Q: How do I use PostgreSQL instead of SQLite?
A: Set DATABASE env vars:
   export TINKER_ENV=production
   export DB_ENGINE=django.db.backends.postgresql
   export DB_HOST=localhost
   export DB_NAME=tinker_db
   export DB_USER=tinker_user
   export DB_PASSWORD=secret

Q: How do I switch environments?
A: Set TINKER_ENV:
   export TINKER_ENV=production
   python manage.py check

Q: How do I verify configuration?
A: Run configuration checks:
   make config-check              # Check it loads
   make config-validate           # Validate structure
   make config-show               # Display settings

Q: What if Dynaconf fails to load?
A: settings.py has fallbacks:
   - Falls back to environment variables
   - Falls back to Python defaults
   - Continues to work with minimal config
