# Requirements Document

## Introduction

Both `ctc-research.com` and `structa.cloud` share the same Django/Wagtail base but differ only in branding and domain-specific features. Currently, a significant portion of business logic — services, managers, middleware, and payloads — is duplicated verbatim across both websites inside a generic `handlers` app. This feature consolidates that shared logic into the appropriate shared packages (`django-osoul` and `django-rseal`), and restructures each website's app layout so that app names reflect their domain purpose rather than generic technical roles.

The work has two orthogonal concerns:
1. **Logic consolidation** — move duplicate code up the dependency chain into shared packages, leaving only thin, site-specific subclasses or shims in each website.
2. **App restructure** — rename/reorganise apps within each website so that the app label and directory name communicate the domain (e.g. `handlers` → `accounts`, `LMS` → `lms`, `pages` → `content`).

## Glossary

- **System**: The combined codebase of `ctc-research.com`, `structa.cloud`, `django-osoul`, `django-rseal`, and `django-grep`.
- **Consolidation_Tool**: The automated or manual process that moves code from website apps into shared packages.
- **django-osoul**: The foundation shared package — pure Django, no Wagtail, no Celery, no django-rseal imports.
- **django-rseal**: The automation shared package — may import Django, django-osoul, Wagtail, and Celery.
- **django-grep**: The testing framework package — provides base test classes, factories, fixtures, assertions, mixins, and pytest plugins for all Django projects in the monorepo.
- **Website**: Either `ctc-research.com` or `structa.cloud`.
- **handlers**: The current generic app in each Website that contains user management, email, services, managers, middleware, snippets, and Wagtail hooks.
- **Domain_App**: A renamed app whose label and directory name reflect its business domain (e.g. `accounts`, `content`, `lms`, `alliance`).
- **Payload / DTO**: A plain Python dataclass or typed dict used to carry structured data between service layers.
- **Wagtail_Hook**: A function or class registered via `@hooks.register` in a `wagtail_hooks.py` module.
- **Snippet**: A Wagtail-managed reusable content object registered with `@register_snippet`.
- **CachedManager**: The base manager class in `django_rseal.pipelines.managers` that provides intelligent cache-backed QuerySet operations.
- **BaseManager**: The base manager class in `django_rseal.pipelines.managers` that provides common QuerySet helpers without caching.
- **Migration**: A Django database migration file generated by `makemigrations`.
- **duplication level**: A measure of code similarity between two code units, expressed as a percentage from 0-100%. A duplication level of 70% or higher indicates significant duplication that should be consolidated.
- **thin subclasses**: Minimal class definitions that inherit from base classes in shared packages and add only website-specific configuration or overrides, with minimal additional logic.
- **shim files**: Temporary compatibility files that re-export functionality from old import paths to new ones, used during migration periods but not recommended for permanent use.
- **dependency graph**: A visual representation of package dependencies showing the allowed direction of imports between packages in the architecture.
- **property-based test**: A testing approach that verifies properties or invariants hold true across a wide range of automatically generated inputs, rather than testing specific examples.
- **Payload**: A structured data transfer object implemented as a Python dataclass with typed fields, used for passing data between service layers.
- **DTO**: Data Transfer Object - synonymous with Payload in this context.
- **Website**: Either `ctc-research.com` or `structa.cloud` (capitalized when referring to the concept, lowercase when used generically).
- **website**: The lowercase form refers to either website instance generically.

## Requirements

### Requirement 1: Identify and Catalogue All Duplicate Logic

**User Story:** As a developer, I want a complete, authoritative inventory of every code unit that is duplicated across both Websites, so that I know exactly what must be moved and nothing is missed.

#### Acceptance Criteria

1. THE System SHALL produce a catalogue listing every Python module, class, and function that exists in both `ctc-research.com/apps/handlers/` and `structa.cloud/apps/handlers/` with a duplication level of 70% or higher.
2. WHEN the catalogue is produced, THE System SHALL classify each duplicate as one of: `extract-to-osoul`, `extract-to-rseal`, `Website-specific` (stays in Website), or `already-extracted`.
3. THE System SHALL include in the catalogue the following confirmed duplicates: `EmailTemplateSelector`, `EmailTemplateRegistry`, `CertificateService`, `CertificateManager`, `PersonService`, `PersonManager`, `MessageService`, `RoleHierarchyManager`, `GroupAccessControl`, `ErrorTrackerMiddleware`, `PrivacyConsentMiddleware`, and `FormSubmissionService`.
4. THE System SHALL record for each duplicate: its current import path in both Websites and its new import path in the shared package.
5. WHILE the System is in the `cataloguing` state, THE System SHALL continue scanning for duplicates until all modules in both `handlers` apps have been processed.
6. THE System MAY optionally include similarity scores for each duplicate entry to help prioritize extraction work.

### Requirement 2: Extract Foundation-Layer Logic to django-osoul

**User Story:** As a developer, I want all pure-Django, Wagtail-free business logic moved to `django-osoul`, so that any Django project can reuse it without pulling in Wagtail or Celery.

#### Acceptance Criteria

1. WHEN a service, manager, or utility has no imports from Wagtail, Celery, or `django-rseal`, THE Consolidation_Tool SHALL place it in `django-osoul`.
2. THE django-osoul package SHALL contain a `RoleHierarchyManager` base class that encapsulates role hierarchy traversal and permission-set computation, with no dependency on any specific Django `Group` name.
3. THE django-osoul package SHALL contain a `GroupAccessControl` base class that provides `check_group_access`, `check_role_access`, `get_accessible_groups`, and `filter_by_group` methods.
4. THE django-osoul package SHALL contain an `ErrorTrackerMiddleware` class that logs 4xx and 5xx responses with request details, with no Website-specific configuration.
5. THE django-osoul package SHALL contain base validator classes (`UniqueFieldValidator`, `SlugFieldValidator`) extracted from Website form validation logic.
6. IF a module being moved to django-osoul contains any import from Wagtail, Celery, or `django-rseal`, THEN THE Consolidation_Tool SHALL split the module so that the Wagtail/Celery-dependent portion remains in `django-rseal` and the pure-Django portion moves to `django-osoul`.
7. THE django-osoul package SHALL maintain zero imports from Wagtail, Celery, `django-rseal`, or any Website app after all extractions are complete.
8. WHILE the System is in the `extraction` state for django-osoul, THE System SHALL validate each extracted module for pure-Django compliance before final placement.
9. THE System MAY optionally provide migration utilities to help Website developers update their imports after extraction.

### Requirement 3: Extract Automation-Layer Logic to django-rseal

**User Story:** As a developer, I want all logic that depends on Wagtail, Celery, or email automation moved to `django-rseal`, so that both Websites share a single maintained implementation.

#### Acceptance Criteria

1. THE django-rseal package SHALL contain a `RoleBasedEmailTemplateSelector` class that provides `get_template_path(role, use_legacy)`, `render_email(role, context, use_legacy)`, `get_role_context(role)`, and `build_context(email, role, **kwargs)` methods, accepting site-specific defaults via constructor arguments or settings.
2. THE django-rseal package SHALL contain an `EmailTemplateRegistry` class that provides `register`, `get`, `list_templates`, and `get_by_role` class methods.
3. THE django-rseal package SHALL contain a `CertificateServiceBase` class that provides `issue_certificate`, `validate_certificate`, `get_certificate_profile`, and `generate_certificate_report` methods, with the concrete `Certificate` model injected via a class attribute.
4. THE django-rseal package SHALL contain a `PersonServiceBase` class that provides `create_person_with_profile`, `get_user_profile_information`, `sync_person_with_user`, `update_notification_preferences`, and `invite_person_to_register` methods.
5. THE django-rseal package SHALL contain a `MessageServiceBase` class that provides `send_message`, `send_bulk_notification`, `get_conversation_thread`, and `get_message_analytics` methods.
6. THE django-rseal package SHALL contain a `PrivacyConsentMiddleware` base class that accepts the list of protected paths and the consent model classes as configuration, with no hard-coded model imports.
7. THE django-rseal package SHALL contain a `FormSubmissionService` class that provides `save_submission`, `send_notification_email`, `get_submissions_for_form`, and `get_submission_stats` methods.
8. WHEN a class is extracted to django-rseal, THE django-rseal package SHALL export it from a stable public API path (e.g. `django_rseal.services`, `django_rseal.email`, `django_rseal.middleware`).
9. WHILE the System is in the `extraction` state for django-rseal, THE System SHALL validate each extracted module for proper dependency isolation from django-osoul.
10. THE System MAY optionally provide configuration templates for Website-specific customization of extracted services.

### Requirement 4: Payload / DTO Placement

**User Story:** As a developer, I want all data transfer objects and payload classes to live in a predictable location, so that services and views can import them without circular dependencies.

#### Acceptance Criteria

1. THE System SHALL place Payload / DTO classes that carry only primitive Python types and stdlib types in `django-osoul` under the exact module path `django_osoul.domain.payloads`.
2. THE System SHALL place Payload / DTO classes that reference Django model instances or Wagtail types in `django-rseal` under the exact module path `django_rseal.payloads`.
3. WHEN a service method returns a structured result, THE service SHALL return either a typed dataclass Payload or a plain `dict` with documented keys — not a mix of both across the two Websites.
4. THE System SHALL define a `CertificatePayload` dataclass with the exact fields: `id` (str), `certificate_id` (str), `name` (str), `issuer` (str), `issue_date` (date), `expiry_date` (date | None), `recipient` (str), `status` (str), `is_verified` (bool), `verification_status` (str).
5. THE System SHALL define a `MessagePayload` dataclass with the exact fields: `id` (str), `subject` (str), `content` (str), `created_at` (datetime), `sender_id` (str), `recipient_id` (str), `is_read` (bool), `read_at` (datetime | None).
6. WHILE the System is in the `payload-placement` state, THE System SHALL validate that each Payload class is placed in the correct package based on its field type dependencies.
7. THE System MAY optionally provide serialization/deserialization utilities for common Payload formats (JSON, YAML).

### Requirement 5: Wagtail-Specific Logic Placement

**User Story:** As a developer, I want a clear rule for where Wagtail hooks, snippets, and blocks live, so that the dependency boundary between django-osoul and django-rseal is never violated.

#### Acceptance Criteria

1. THE System SHALL keep all `wagtail_hooks.py` files inside the Website apps; Wagtail_Hook registrations SHALL NOT be placed in `django-osoul`.
2. WHERE a Wagtail_Hook contains reusable logic (e.g. permission checks, menu construction), THE System SHALL extract that logic into a helper function in `django-rseal` under `django_rseal.wagtail_helpers` and call it from the Website's `wagtail_hooks.py`.
3. THE System SHALL keep all Snippet model definitions inside the Website apps or in the exact module `django_rseal.pipelines.snippets`; Snippet models SHALL NOT be placed in `django-osoul`.
4. THE System SHALL keep all StreamField Block definitions inside the Website apps or in `django-rseal` under `django_rseal.blocks`; Block definitions SHALL NOT be placed in `django-osoul`.
5. WHEN a Block or Snippet references a model that is already in `django-rseal.pipelines.models`, THE System SHALL import that model from `django-rseal` rather than duplicating it in the Website app.
6. WHILE the System is in the `wagtail-logic-review` state, THE System SHALL validate that no Wagtail imports exist in django-osoul.
7. THE System MAY optionally provide base Block classes in django-rseal for common Wagtail block patterns.

### Requirement 6: App Restructure — Rename to Domain-Aligned Names

**User Story:** As a developer, I want each app in both Websites to have a name that reflects its business domain, so that the codebase is self-documenting and new contributors can navigate it without a guide.

#### Acceptance Criteria

1. THE System SHALL rename the `handlers` app in `ctc-research.com` to `accounts`, updating the `AppConfig.name` to `"apps.accounts"`, `AppConfig.label` to `"accounts"`, all `INSTALLED_APPS` entries, all URL includes, and all cross-app imports.
2. THE System SHALL rename the `handlers` app in `structa.cloud` to `accounts`, applying the same changes as criterion 1.
3. THE System SHALL rename the `LMS` app in `ctc-research.com` to `lms`, updating `AppConfig.name` to `"apps.lms"`, `AppConfig.label` to `"lms"`, `INSTALLED_APPS`, URL includes, and all cross-app imports.
4. THE System SHALL rename the `LMS` app in `structa.cloud` to `alliance`, updating `AppConfig.name` to `"apps.alliance"`, `AppConfig.label` to `"alliance"`, `INSTALLED_APPS`, URL includes, and all cross-app imports.
5. THE System SHALL rename the `pages` app in both Websites to `content`, updating `AppConfig.name` to `"apps.content"`, `AppConfig.label` to `"content"`, applying the same changes as criterion 1.
6. WHEN an app is renamed, THE System SHALL generate a new Django Migration that renames the database table prefix from the old app label to the new app label for every model in that app.
7. THE System SHALL update all `content_type` references (e.g. `ContentType.objects.get(app_label=...)`) to use the new app label after the rename.
8. WHILE the System is in the `app-rename` state for a specific Website, THE System SHALL complete all rename operations for that Website before proceeding to the next Website.
9. THE System MAY optionally provide a rollback script for each app rename operation in case of migration issues.

### Requirement 7: Sub-App Naming Within Domain Apps

**User Story:** As a developer, I want the internal module structure of each Domain_App to use consistent, descriptive sub-module names, so that I can find any piece of logic in under 30 seconds.

#### Acceptance Criteria

1. THE System SHALL organise each Domain_App using the following mandatory sub-module layout: `models/`, `services/`, `managers/`, `forms/`, `views/`, `filters/`, `middleware/`, `admin/`, `migrations/`, `templates/`, `templatetags/`, with optional `snippets/` (Wagtail only), and `wagtail_hooks.py` (Wagtail only).
2. THE System SHALL ensure that each sub-module contains only code of its declared type (e.g. `services/` contains only service classes, `managers/` contains only Django manager classes).
3. WHEN a sub-module in a Domain_App contains only a thin subclass that delegates to a shared package, THE System SHALL add a module-level docstring stating the exact canonical import path in the shared package.
4. THE System SHALL not create sub-modules named `handlers`, `processors`, or `registration` in the restructured Domain_Apps; logic from those directories SHALL be redistributed into the standard sub-module layout.
5. WHILE the System is in the `submodule-restructure` state for a Domain_App, THE System SHALL validate that all code has been correctly redistributed before marking the restructure complete.
6. THE System MAY optionally provide linting rules to enforce the standard sub-module layout in future development.

### Requirement 8: Direct Import Updates — No Deprecation Shims

**User Story:** As a developer, I want all import statements updated in-place to point directly to the new canonical locations, so that the codebase has no dead-weight compatibility layers and every import is immediately self-documenting.

#### Acceptance Criteria

1. WHEN a class or function is moved from a Website app to a shared package, THE System SHALL update every import statement across both Websites to reference the exact new canonical path directly — no shim files SHALL be created.
2. WHEN an app is renamed, THE System SHALL update every `from apps.<old_name>` and `import apps.<old_name>` statement in both Websites to use the new app name.
3. THE System SHALL perform a codebase-wide search using `grep -r` for all old import paths before deletion to confirm zero remaining references before removing the original module.
4. WHEN a module is moved, THE System SHALL delete the original file from the Website app after all imports have been updated and all tests pass with zero failures.
5. THE System SHALL verify zero remaining references to old import paths by running a comprehensive grep/search across the entire codebase as a final validation step.
6. WHILE the System is in the `import-update` state, THE System SHALL process imports in batches and verify each batch before proceeding to the next.
7. THE System MAY optionally provide automated import update scripts for common migration patterns.

### Requirement 9: Migration Safety and Database Integrity

**User Story:** As a developer, I want all database migrations to be safe and reversible, so that I can roll back any rename or restructure without data loss.

#### Acceptance Criteria

1. WHEN an app label is changed, THE System SHALL generate a Migration that uses `RenameModel` or `AlterModelTable` to preserve existing data in the renamed table.
2. WHEN a model is moved from a Website app to a shared package, THE System SHALL generate a Migration that uses `SeparateDatabaseAndState` to avoid dropping and recreating the table.
3. THE System SHALL verify that all Migrations are reversible by running `python manage.py migrate --fake-initial` and `python manage.py migrate <app> zero` in a test environment before merging, with zero errors.
4. WHEN a `ForeignKey` or `ManyToManyField` references a model whose app label has changed, THE System SHALL update the `app_label` in the field's `to` argument and generate the corresponding Migration.
5. THE System SHALL run the full Django test suite (`pytest` with coverage) against both Websites after all Migrations are applied, with zero test failures.
6. WHILE the System is in the `migration-testing` state, THE System SHALL test each migration individually before testing the complete migration sequence.
7. THE System MAY optionally provide migration rollback scripts for emergency recovery scenarios.

### Requirement 10: Dependency Direction Enforcement

**User Story:** As a developer, I want the dependency direction `stdlib → nawaai → django-osoul → django-rseal → Websites` to be enforced automatically, so that architectural violations are caught before they reach production.

#### Acceptance Criteria

1. THE System SHALL add a `lint-imports` step to the CI pipeline that uses `import-linter` with configuration file `.importlinter` to assert that `django-osoul` has zero imports from `django-rseal`, Wagtail, or Celery.
2. THE System SHALL add a `lint-imports` step that asserts `django-rseal` has zero imports from any Website app.
3. THE System SHALL add a `lint-imports` step that asserts `nawaai` has zero imports from Django, `django-osoul`, or `django-rseal`.
4. WHEN a developer introduces a circular import or an upward dependency, THE CI pipeline SHALL fail with an error message that includes: the violating import statement, file path, line number, and suggested fix.
5. THE System SHALL document the dependency rules in a `ARCHITECTURE.md` file at the repository root, including a Mermaid.js dependency graph diagram.
6. WHILE the System is in the `dependency-enforcement` state, THE System SHALL run import-linter checks after each code change to detect violations early.
7. THE System MAY optionally provide IDE plugins or pre-commit hooks to catch dependency violations during development.

### Requirement 11: Testing — Property-Based and Integration Tests

**User Story:** As a developer, I want comprehensive tests for all extracted logic, so that I can be confident the consolidation has not changed observable behaviour.

#### Acceptance Criteria

1. THE System SHALL include a property-based test asserting that `RoleBasedEmailTemplateSelector.get_template_path(role)` always returns a non-empty string for any non-empty string `role` input, using Hypothesis with `@settings(max_examples=100)`.
2. THE System SHALL include a property-based test asserting that `RoleBasedEmailTemplateSelector.build_context(email, role)` always returns a dict containing the exact keys `email`, `role`, `site_name`, `site_url`, and `support_email` for any valid `email` and `role` inputs.
3. THE System SHALL include a property-based test asserting that `RoleHierarchyManager.get_all_permissions_for_role(role)` is idempotent: calling it twice with the same `role` returns the same set.
4. THE System SHALL include a property-based test asserting that `RoleHierarchyManager.get_role_hierarchy(role)` always includes `role` itself as the first element for any defined role.
5. THE System SHALL include a property-based test asserting that for any valid `CertificatePayload`, serialising to dict and reconstructing the dataclass produces an equivalent object (round-trip property).
6. THE System SHALL include an integration test for each extracted service that verifies the service produces the same result when called from `ctc-research.com` and from `structa.cloud` with equivalent inputs (minimum 3 test cases per service).
7. WHEN the `PersonManager.get_or_create_for_user` method is called with the same user twice, THE test SHALL assert that the second call returns the existing person and `created=False` (idempotence property).
8. THE System SHALL include a property-based test asserting that `MessageService.get_conversation_thread` pagination is consistent: the union of all pages equals the full conversation, with no duplicates and no gaps.
9. WHILE the System is in the `test-execution` state, THE System SHALL run all property-based tests with different random seeds to ensure robustness.
10. THE System MAY optionally include performance benchmarks for critical service methods to detect regression.

### Requirement 12: Documentation and Migration Guide

**User Story:** As a developer, I want a clear migration guide that explains every import path change, so that I can update any downstream code without guessing.

#### Acceptance Criteria

1. THE System SHALL produce a `MIGRATION_GUIDE.md` document listing every changed import path in the exact format: `OLD: apps.handlers.email_templates.EmailTemplateSelector → NEW: django_rseal.email.template_selector.RoleBasedEmailTemplateSelector`.
2. THE System SHALL produce an `ARCHITECTURE.md` document containing a Mermaid.js dependency graph, a description of each shared package's responsibility, and the exact rules for deciding where new code belongs.
3. THE System SHALL update the `README.md` of `django-osoul`, `django-rseal`, and `django-grep` to document all newly added public classes with: purpose, parameters, return type, and at least one usage example.
4. WHEN a new public class is added to a shared package, THE System SHALL include a docstring with: purpose, parameters (type-annotated), return type (type-annotated), and at least one usage example.
5. THE System SHALL document the app rename mapping in `MIGRATION_GUIDE.md` in a table format: `handlers → accounts`, `LMS (ctc) → lms`, `LMS (structa) → alliance`, `pages → content`.
6. WHILE the System is in the `documentation` state, THE System SHALL validate that all documentation is complete and accurate before marking documentation tasks complete.
7. THE System MAY optionally provide interactive migration tools or scripts to help developers update their code.

### Requirement 13: Test Migration to django-grep

**User Story:** As a developer, I want all existing tests in both Websites to use `django-grep` base classes, factories, and utilities, so that test infrastructure is shared and maintained in one place.

#### Acceptance Criteria

1. THE System SHALL migrate all test files in `ctc-research.com/tests/` and `structa.cloud/tests/` to import base test classes from `django_grep.tests.base` rather than directly from `django.test`.
2. THE System SHALL migrate all test factories in both Websites to use `django_grep.tests.factories` as the base, replacing any inline `factory_boy` or manual object creation patterns.
3. THE System SHALL migrate all custom test assertions in both Websites to use `django_grep.tests.assertions`, adding any missing assertion helpers to `django-grep` as part of this work.
4. THE System SHALL migrate all test fixtures in both Websites to use `django_grep.tests.fixtures` for loading and creating test data.
5. THE System SHALL migrate all test mixins (e.g. search, filter, pagination test helpers) in both Websites to use `django_grep.tests.mixins`.
6. WHEN a test utility does not yet exist in `django-grep`, THE System SHALL add it to `django-grep` before migrating the Website test that depends on it.
7. THE System SHALL add property-based test helpers to `django_grep.tests.base` that wrap `hypothesis` strategies for common Django model fields (e.g. `st_email()`, `st_slug()`, `st_uuid()`), so that both Websites can use them without importing `hypothesis` directly.
8. THE System SHALL ensure that after migration, running `pytest` in either Website produces zero import errors related to test infrastructure.
9. THE System SHALL add a `conftest.py` entry in `django-grep` that registers the pytest plugin (`django_grep.tests.pytest_plugin`) so both Websites can activate it via `pytest.ini` or `pyproject.toml` without duplicating fixture definitions.
10. WHEN a test in either Website tests behaviour that is now in a shared package, THE System SHALL move that test to the shared package's own test suite (`venv/libs/django-grep/tests/` or the package's `tests/` directory) and replace the Website-level test with a thin integration call.
11. WHILE the System is in the `test-migration` state, THE System SHALL migrate tests in batches and verify each batch compiles and runs successfully.
12. THE System MAY optionally provide automated migration scripts for common test patterns.
